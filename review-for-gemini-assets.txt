# 项目背景（读懂这份设计需要的最小上下文）

- Apollo 是一个**数据驱动游戏引擎**：最高纲领是「游戏 = 数据，代码只属于引擎这台固定的确定性解释器」。
  判据尺子：「最弱的 LLM 能不能也产出一模一样的数据？」能 → 走数据接口；不能（要写自由代码）→ 拒绝。
- 产品愿景：「小白一句话成游戏」。护城河逻辑：**质量沉淀在策展资产里，AI 只做选/填/补，不做从零裸生成**
  （裸生成 = gameslop）。这套逻辑已用在「模块库」上（策展库 + AI 语义选择 + 生成增量 + 占位兜底）。
- 引擎已有：确定性 2D 物理/ECS、Condition→Event→Effect 涌现层、对话解释器（dialogue）、三消解释器
  （match3-board）、渲染器（贴图 R1）、音频后端（R8）、输入接缝、studio 透视器 + manifest 桥接（导出↔导入）。
- **当前缺口**：引擎**零资产侧**——无资产清单契约、无策展库、无生成集成、无管理器工具。
  本设计就是补这条腿（与「模块库」并列的护城河第二条腿：Skin 层契约 + 工具）。
- 关键架构约束（务必带进 review）：
  · `EnginePort`：表现/IO 是可插拔后端，逻辑核心不依赖具体实现。
  · **确定性边界**：逻辑核心只引用稳定的 `slot.id` 字符串；像素/音频**不进模拟哈希** →
    填充/重生成不破坏 lockstep / 录放确定性。
  · AIGP（生成式美术）走**表现层旁路**，不进 sim（周期表 X5 SemanticMaterial / X7 LatentAnchor）。

# Asset Manifest & Asset Manager — 资产清单与资产管理器设计

定位：Skin 层契约 + 工具——与"模块库"并列的护城河第二条腿。

## 0. 一句话
引擎附带一个**"待填充（To-Be-Filled）资产清单"数据结构** + 一个**资产管理器工具**：打开它就知道这个
游戏**还差哪些资产、各叫什么、什么描述、什么规格**；用户在引导下**一步步填**，填法有四条（一键生成 /
从库选 / 手动上传 / 程序化占位），AI 只是其中一条路径，**人始终在环、保留掌控**。

## 1. 战略定位：为什么是"契约 + 人在环"，不是"AI 全自动出图"
护城河逻辑对美术同样成立：每张图现 call 文生图从零生成 → 角色跨表情换脸、跨场景画风漂移、风格不统一、
版权/安全失控。正解与模块 pipeline 同构：策展库（护城河）+ AI 语义选择（智能导购）+ 生成式增量（增强）
+ 程序化占位（永远能跑的兜底），**重心放在契约（数据结构）上**，而不是某个生成模型上。
关键差异化：交付的不是"生成器"，是**资产契约 + 管理器工具**。生成后端可替换，契约不变。

## 2. 核心数据结构：Asset Manifest（TBF 清单）
### 2.1 槽位 Schema（每条 = 一个待填充资产槽位）
- id (string)：稳定槽位 id（如 char_S.portrait、bg.office）。逻辑核心只引用它，永不引用二进制。
- category (enum)：background｜character_portrait｜cg｜ui_theme｜icon｜bgm｜sfx｜voice
- name (string)：人类可读名。
- description (string)：语义描述，既给人看、又作文生图 prompt 种子。
- requiredBy (string[])：溯源——哪些场景/实体/模块引用它。
- spec (object)：技术规格 = 规范化目标（type, width, height, aspect, transparent, anchor, format, duration, loop）。
- consistencyGroup (string?)：同组 = 同一人/同一画风，必须成套填（立绘多表情、跨场景同角色）。
- anchorRef (string?)：一致性锚点 id → 锁身份/画风（X7 LatentAnchor），防换脸/漂移。
- variants (object[]?)：差分子项（表情差分等）：{ key, description }，作为一致的一套生成/上传。
- tags (string[])：供策展库语义检索。
- status (enum)：empty｜placeholder｜filled｜approved。
- fill (object?)：填充溯源：{ method:'procedural｜library｜generative｜upload', source, license, seed?, prompt?, ref }。

### 2.2 status 生命周期
(创建槽位) → placeholder →(某 provider commit + 规范化)→ filled →(人确认)→ approved
（filled 可重填/重生成回 filled）。槽位一创建即落 placeholder（程序化占位）→ 游戏从第一刻起就能跑、
永远能跑，填充是渐进的。approved = 人类拍板的最终态；导出正式包只认 approved（或可配置降级到 filled）。

### 2.3 一致性组与锚点（X5 / X7）
裸生成最大命门是一致性：consistencyGroup 把同组槽位作为一套处理（同批出、同 anchorRef）；
anchorRef → X7 LatentAnchor 锁角色身份/全局画风（seed / reference image / IP-Adapter，依后端，先留抽象）；
ui_theme 槽位关联全局画风锚点 → 背景、立绘、UI 风格统一（X5 SemanticMaterial）。

### 2.4 示例（Game B 节选）：styleAnchor + slots[]（bg.office 背景 / char_S.portrait 立绘带 5 表情 variants
+ consistencyGroup+anchorRef / bgm.daily 音乐）。

## 3. 自动派生：清单从蓝图来（开发期 / 产品期统一）
清单**不手工维护，从游戏蓝图/内容自动聚合**——和"模块 manifest 聚合成 Game Manifest"同构：
蓝图/内容声明它引用的资产槽位（Sprite.textureKey="char_S.portrait@neutral" 等语义引用）；
构建期扫描所有引用 → 去重 → 生成 Asset Manifest（带 requiredBy 溯源）。
同一结构服务两端：开发期 = "还差哪些美术"的活规格；产品期 = 交给管理器让小白填。共用同一套契约。

## 4. 填充 Provider 接口（可插拔四路，同一契约）
interface AssetProvider { id:'procedural'|'library'|'generative'|'upload'; canFill(slot); propose(slot,ctx):Candidate[]; commit(slot,choice):RawAsset; }
- procedural：SVG/CSS 程序化占位，零依赖永远兜底（默认）。
- library：策展库语义检索，给 3–4 个好选项（智能导购）。
- generative：按 description+anchorRef 调文生图/文生乐，同组成套出（小白「一键生成」）。
- upload：手动传文件 → 进规范化（老手）。
四条路都往同一个槽位契约写 fill。

## 5. 资产管理器（引擎附带工具，UX）
按 category/场景分组的清单 + 进度条；每槽一行：名字 + 描述 + 预览 + status + provider 按钮；
consistencyGroup 作为一套操作（整组生成/上传）；填充即 provider commit → 规范化 → status=filled + fill 溯源；人确认 → approved。

## 6. 规范化流水线
无论来源，落库前统一到 spec：interface Normalizer { process(raw, spec):NormalizedAsset; }
（抠图 / 统一尺寸锚点 / 打图集 / 压缩 / 格式转换 / 版权安全过滤）。

## 7. 与运行时对接 & 确定性边界
- AssetResolver：slot.id →（filled/approved 取真资产，否则取 placeholder），保证缺资产也可玩。
- 加载：经 EnginePort.asset.preload(bundle) 预载；view.spawn(entity, visualType=slot.id) 映射到解析结果。消费端 = R1 贴图 / R8 音频。
- 确定性：资产是表现层，逻辑核心只引用 slot.id，像素/音频不进模拟哈希 → 填充/重生成不破坏 lockstep/录放。

## 8. 归属与分期
- 现在能做（不阻塞 Game B）·PB：定义 Game B 槽位契约实例；实现 procedural 占位 provider；蓝图里用语义引用挂槽位。
- 需立项（框架级，Lead 拥有 canonical）：canonical schema + AssetResolver + Provider 接口；library 检索；
  generative 集成 + X7 锚定；规范化流水线；资产管理器 UI。
- Game B 是第一个、也最吃资产的验证消费者（多角色×多表情 + 多背景 + UI 主题 + BGM/语音）。

## 9. 给 Reviewer 的开放问题（★ 请 Gemini 重点回答）
1. canonical schema 落点：放哪个包/路径？每游戏一份 asset-manifest.json vs 从 Game Manifest 聚合派生——
   设计倾向后者（§3），请确认是否同意、有无坑。
2. Provider 是否并入 EnginePort 家族，还是独立 AssetPort？（生成/上传是编辑期能力，运行期只需 asset.preload
   —— 可能该分两层：编辑期 AssetAuthoringPort vs 运行期 AssetPort？）
3. 一致性锚定（X7）实现路径：seed lock / reference image / IP-Adapter？依赖生成后端，先留抽象接口是否可接受？
4. 生成后端选型 + 网络/key 策略：Gemini image / SDXL / 本地？谁持有 key、什么网络策略放行？
5. 版权 / 安全过滤归谁、在规范化哪一步？
6. procedural 占位规格：占位要"能看"到什么程度才够验证手感/演出（纯色块够吗，还是简笔立绘 + 表情符号）？
7. 导出策略：正式包认 approved 还是可降级 filled？缺 approved 时是否允许带占位发布？
