# 参考库 · 极逸 Soon（AI 游戏创作平台）

> 加入 ref 的同类平台分析（来源：从业者实测长文）。目的同 OpenGame：理解其设计 → 与 Apollo 对比 → 架构师裁哪些可吸收、哪些刻意不学。

## 1. 它是什么
- **Web H5 游戏生成平台**：Node + TypeScript + Vite 工程；**PixiJS 8 + Spine（骨骼动画）** 渲染；包 `agent-gamedev` / `agent-gamedev-plugins`。
- **多模态输入**：视频 → **结构化意图**（对象 / 规则草案 / 交互密度 / 镜头节奏）→ 再生成（不是像素拷逻辑）。
- **Skill 驱动流水线**（`game-builder`）：对话 → 任务链；阶段闸门 **设计→资源→初始化→实现→验证**，失败回退到查文档 + 增量修补（非全量重生）。
- **生成前先冻结世界模型**：显式加载 **ECS / Scene / API 约束**——等于给代码生成器一份"施工图纸 + 调用边界"。
- **API Reference 当可检索真理源**（RAG + 受限语法）：模型遇到不确定 API 回查文档对齐签名，而非发明接口。
- **数值子引擎**（TS、零依赖、<50KB）：公式/曲线用数据描述、运行时解析；元数据→运算→实例绑定→运行时观测→外部表格回流；Runtime +（可选）可视化配表编辑器。
- **骨骼动画管线**：骨骼模板/类型 + rig 修正 + 动画时间轴/事件帧 + AIGC 出图 + 导出 json/atlas/png（覆盖 编辑-预览-导出-运行时消费 闭环）。
- 成熟度：社区已有完成度不低的作品（如肉鸽卡牌《旧日迷城》）。

## 2. 核心异同（一句话抓住）
**Soon = 业界一流的"受约束代码生成"；Apollo = "不生成代码、只产受约束数据"。**
两者共享同一套上下文工程洞察——① 收窄生成空间 ② 把不确定性外置到可检索文档 ③ 阶段闸门 + 增量修补 + 自校验。区别在**把约束推到哪**：
- Soon 把模型关进"少数代码范式 + API 参考"里写 **TS/JS 代码**；ECS 是生成代码要遵守的**纪律**。产物是**代码库**，正确性仍依赖模型 + 修复循环（文中自承："AI 改不好/幻觉时仍需专业工程师支援"）。
- Apollo 让模型只产 **manifest 数据**（capabilities + entities）；ECS 是**固定的确定性运行时**，不是代码风格。代码（capability 库）永不被生成；非法数据被 **R12 校验器**直接拒、能力是**闭合词表**。→ **最弱的 LLM 和最强的产同一种数据**。

> Soon 用工程实践**验证了我们的方向**；Apollo 是同一条"收窄生成空间"轴上的**极限点**（窄到只剩数据），因此更模型无关、更可验证；代价是当前**广度/成熟度**不如 Soon（它有 Pixi/Spine/数值引擎/视频输入/社区）。

## 3. 逐维对比
| 维度 | 极逸 Soon | Apollo（我们） |
|---|---|---|
| AI 产物 | **受约束的 TS/JS 代码** | **纯数据 manifest**（capabilities+entities） |
| 约束方式 | ECS 纪律 + API Reference + 阶段闸门 + 自修复 | 能力注册表(闭合词表) + R12 校验 + ApolloBench + 不可变 edit-ops |
| 模型依赖 | 仍依赖(幻觉需工程师救) | **结构性无关**(非法数据被拒,不会带病上线) |
| 确定性/回放/联机 | 生成代码无保证 | 确定性 hash + 快照/回放 + lockstep |
| 编辑方式 | 重生成/补丁**代码** | 编辑**数据**(强类型投影 + 模型无关 edit-ops + 校验) |
| 资产/动画 | **Pixi+Spine 骨骼管线 + AIGC 出图**（强） | 资产清单 TBF + Canvas Sprite（弱，待补） |
| 数值 | **公式/曲线数值子引擎 + 配表编辑器 + 表格回流**（强） | Resource/Condition/Effect（逻辑数值，无公式 DSL） |
| 输入 | **视频→结构化意图**（强） | 文本/预设 → manifest（无视频/无中间意图层） |
| 成熟度 | 有社区作品 | 早期 |

## 4. 我们能学什么（直接回答原文 Q4：上下文工程 + 约束 AI）
Soon 的三招正是我们已经在做的，逐条对照：
- **生成前冻结世界模型 + 调用边界**（Soon 先载 ECS/Scene/API）→ 我们的**能力注册表 + 自描述 schema 就是冻结的世界模型**，当作"菜单"喂模型。✅ 已做。
- **把不确定性外置到可检索真理源**（API Ref = RAG + 受限语法）→ 我们的 schema/registry 即真理；edit-resolver 对着它模糊吸附。✅ 部分；可加**检索/裁剪**(只喂相关子集，= 上下文限定)。
- **收窄生成空间到少数范式**→ Apollo 是**最窄**：根本不产代码,只产数据。✅✅ 我们比它更窄。
- **阶段闸门 + 增量补丁 + 自校验**→ edit-ops 是增量补丁,R12 校验,ApolloBench 打分。✅ 有零件;接 LLM 时可把它**编排成显式闸门 + 有界重试循环**(对应 Soon 的"查 API→改")。
- **结构化意图中间层**（视频/NL → 结构化意图 → 生成）→ 我们**缺**;这是该吸收的(也呼应 OpenGame 的 GDD-first)。

## 5. 吸收清单（架构师裁决）
- ✅ **被验证、继续**：数据-only + 注册表 + R12 + ApolloBench + edit-ops。这正是我们对 Soon 的护城河（更模型无关）。别动摇。
- 🟢 **吸收（合纲领、可做）**：
  - **结构化意图层**：NL/视频 → 一份小的"游戏意图(对象/规则/节奏)"数据 → 再装配 manifest。收窄生成空间、降发散。
  - **检索-接地 + 上下文限定**：只把"相关能力/字段子集"喂模型（编辑器设计文档已列）。
  - **显式阶段闸门 + 有界修复循环**：把 LLM-编辑路径做成 校验→回错→重试→体检 的流水闸门。
- 🟡 **吸收但要"数据化"（不照 Soon 写代码）**：
  - **数值公式 DSL**：用**数据描述的表达式 AST** + 一个 `formula/curve` capability 解释执行——这是 manifesto 的方式拿到 Soon 数值引擎的能力，而**不是**再造一个会生成代码的数值引擎。重数值品类（RPG/卡牌）需要时再下沉。
- 🔵 **大件、缓做（真有价值但重，属表现/资产层、后端可换）**：骨骼动画/Spine 管线 + 动画编辑器；视频输入；Pixi 渲染后端。列路线图，不现在做。
- ❌ **刻意不学（回驳）**：Soon 的"生成受约束**代码** + 自修复"主循环。那恰是我们数据-only 要**避免**的——它把模型依赖 + 幻觉(需工程师救)重新引回来。**我们的差异化就是不生成代码。** 即便 Soon 证明了它可行，我们也不该往代码生成转。
