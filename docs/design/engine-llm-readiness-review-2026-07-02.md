# Apollo 引擎「面向 LLM 的轻量游戏引擎」如实评审（2026-07-02）

> owner 委托：对原子架构 + 能力积木做 review，以 game-e（小丑牌）、game-g（翻命扑克）、game-d（骰途/骰盅）为样本，
> 如实判定本引擎「未来竞争力」与「弱 LLM 产出游戏的能力」。
> 尺子 = 宪法 `data-driven-manifesto.md` §6（最弱 LLM 能否产出一模一样的东西）+ §7（数据 vs 代码占比）。
> 方法：主程（xhigh）裁决 + 4 个子代理逐文件体检（能力库盘点 ×1、游戏深读 ×3），全部结论带 file:line 证据。

---

## 一、总判定（先说结论）

**判定：结构成立，执行欠账。有真实潜力，但今天还不是「弱 LLM 能产出游戏」的引擎——是「弱 LLM 能产出游戏内容」的引擎。**

分层打分（如实）：

| 层 | 现状 | 弱 LLM 今天能否交付 |
|---|---|---|
| **内容层**（牌表/英雄/关卡/音效/主题） | ✅ 真数据，三游戏一致验证 | **能**，且有测试兜错 |
| **规则层**（回合流程/结算/修正聚合/AI） | ❌ 三游戏各自手写三套同构代码，引擎已有的卡牌能力全被绕过 | 不能 |
| **UI 层** | 🔶 LayoutNode 库真实可用（game-g 大厅六屏达标），但 builder 必须是 TS 函数 | 不能 |
| **装配/验证管线**（manifest→校验→bench） | ✅ 闭环真实存在，但生产上零游戏使用 | 管线可用，无人走 |

三游戏加权硬指标（宪法 §7）：**纯数据 ≈ 23%，胶水 ≈ 34%，自由代码 ≈ 43%**（目标 100% 数据）。
逐游戏：game-e 31/21/48（剔除入口 tsx 后 50/31/20）· game-g 21/46/33 · game-d 12/15/72。

弱 LLM 只写数据的复刻率判定：**game-e ≈ 35-40% · game-g ≈ 20-25% · game-d ≈ 12%（理论上限 70-85%）**。

## 二、引擎底座盘点（这部分是真金）

- **78 个注册 capability**：29 原子（注释口径仍写 26，漂移）+ 8 tier1 + 31 tier2 + 9 tier3（`capability-registry.ts:57-111`）。
- **纯 JSON manifest 闭环真实存在且设计正确**：`{capabilities, entities}` 纯 JSON 可表达、**塞不进函数**（`manifest.ts:36-107`）；能力目录自动导出喂 LLM（`capability-catalog.ts:28-43`，"零 prompt 维护"）；`apollo.py` 五路 LLM provider 生成 → parseManifest 校验 → 透视器可跑；**ApolloBench** 无浏览器五轴体检，含确定性双跑同 hash（`apollo-bench.ts:7-23`）。
- **UI 库 LayoutNode**：34 种控件闭集 + 全量自描述 catalog（喂 LLM/校验/样例三用）+ validateLayoutNode 五类校验；特效/颜色/字体全闭集枚举。
- **测试面**：skills 88 个测试文件 9,492 行，测试:源码 ≈ 1.09:1；全仓 277 个测试文件。
- **配套论证文档已存在**：`ai-data-editor.md`（LLM=受限表单填写器）、`weak-llm-thesis-redteam.md`（命题红队自审）——说明团队对命题风险有自觉。

**这套底座在同类里是少见的完整**：市面上要么表达力极窄（PuzzleScript/Bitsy），要么庞大不轻量（GDevelop/Construct），要么放任 LLM 写自由代码（方差不可控）。Apollo 的差异化——**确定性、可审计、可 diff、双跑同 hash、LLM 方差归零**——是真实存在的，而且不随 LLM 变强而贬值（agent 时代"可验证的产物"反而更值钱）。

## 三、但硬伤同样真实（如实揭短）

### 3.1 生产上零游戏走纯数据管线
`parseManifest` 全仓的生产消费方**只有 launcher/Studio 透视器**（`launcher.tsx:743-1147`）。8 个在营游戏全部是 TS 代码路径，游戏侧非测试代码共 **19,362 行**。宪法管线和真实游戏是**两个平行世界**：manifest 路是给 demo/生成器走的，真游戏没有一个吃过自己的狗粮。

### 3.2 三套同构的自炉灶——规则层词汇缺口是收敛的，但没人下沉
三个游戏各自手写了高度同构的规则核：
- game-e：`session.ts` 回合编排 + `jokerToEntities` 游戏层编译器 + 经济解释器（~310 行 C）
- game-g：`turn-combat.ts` 679 行 + `clash-resolve.ts` + 天罡/地煞两套修正聚合解释器（~810 行 C）
- game-d：`combat.ts` 手写牌型判定——**与引擎现成的 `poker-hand` 能力同构却独立重写**（`combat.ts:103-126` vs `poker-hand.ts:188-282`）

其中**「修正聚合/加成栈」在仓库里已经重复了三次**（game-e joker 效果、game-g 天罡、game-g 地煞），字段表 + merge 策略 + 条件门控的模式完全一致。这是全仓最高价值的下沉点。引擎明明已有 `flow`/`card-pile`/`card-play`/`effect-apply`/`event-when`，三个游戏一个都没接。

### 3.3 UI 是最大单一负债，且现有铁律治不了根
- game-e：1,163 行**手写 React 零 LayoutNode**——CLAUDE.md 给它的豁免理由（"本就走引擎渲染器"）**与事实不符**：引擎渲染器视图 `view.ts` 存在但全仓零消费方。回合流程还在 session.ts 和 game-e.tsx 里**存了两份重写的真相**。
- game-g：大厅六屏真达标（零手写 DOM）；但战斗屏是混血——540 行 LayoutNode 节点 + 330 行手写 HTML 壳/mount/FLIP + 64 行手写 CSS 关键帧 + game-g.tsx 里 6 处裸 innerHTML 浮层 + coin-flip.ts 整文件死代码。
- **更深的问题**：即使 100% 守铁律，LayoutNode builder 也必须是带条件分支的 TS 函数（game-g 约 1,700 行）——**弱 LLM 交付不了函数**。缺的是「数据→视图」绑定层（模板 + 绑定表达式），没有它 UI 永远有 40-50% 是代码。

### 3.4 数据面虚胖——填了数据、没有解释器
- game-g：36 天罡里**约 18 张**（tempo/lane/arcane 印记/擒王）无任何 handler，"未实装 kind 返回零修正、不崩"（`game-g-build.ts:55`）；52 boss×3 地煞共 156 条里**只有 15 张实装**，其余 141 条是超出 DishaFx 数值旋钮的纯文案。
- game-e：150 张小丑目录里 **82 张不可执行**（复制/造牌/改牌组类），`text` 是英文人话不是可执行语义。

**这对 LLM 引擎是特有的危险**：LLM 会照着"假样例"继续批量生产假数据，表面数据率上升、实际可执行率下降。数据表假装了一个不存在的解释器，比没有数据更糟。

### 3.5 校验是体检不是闸门
- manifest 字段校验只硬查 number/boolean；string/数组/嵌套对象（恰是 dialogue/GameFlow/Prefab 这些最复杂的数据）**不校验**（`validate-manifest.ts:17-18` 自认）；assetKey 校验是 opt-in。
- 引用断链全部 warning 不拦截，运行期**静默吞**（`validate-references.ts:7-12`）。
- validateLayoutNode 对未列字段宽松（props 塞任意键不报）。
- ApolloBench 只测 2 个对象：demo + **已冻结的 game-f**；在营的 g/h/i/x/z 全不在 bench 里。
- 对人类程序员这叫宽松；**对 LLM 用户这叫没有护栏**——弱 LLM 恰恰需要 error 级的硬反馈才能自我纠正。

### 3.6 纪律执行比能力缺口更拖后腿（game-d 是反面标本）
game-d 的问题几乎全不是"引擎做不到"：`capabilities: []` 零接入；用裸 `Math.random()` 绕开引擎种子化 PRNG（不可回放、双人无法同步，且与自己 gdd §11.1 的承诺矛盾）；手写牌型判定重复 poker-hand；双人按钮是假的（两个按钮绑同一个单人 start）；0 测试；平衡仿真台是 combat.ts 的**手工平行重写**（"一处调两处同步"，无一致性断言）。它自己的 gdd 映射表证明理论上限 70-85% 纯数据，实际 12%。**宪法有了、能力有了，但没有任何机制强制走数据路径。**

### 3.7 文档口径漂移（小但要修）
"26 原子"实为 29（4 处文档未同步）；CLAUDE.md 关键文件仍指向已删除的 game-a/b/c；game-e 的 UI 豁免理由失实；launcher 卡片文案过期。

## 四、竞争力判定（面向未来）

**风险一（必须直面）：「弱 LLM 也能产出」这个卖点本身在贬值。** 模型只会更强更便宜，"补偿弱模型"不是长期护城河。但本引擎真正的护城河其实一直不是这个，而是：
1. **一致性**：强弱模型产出同样的数据 → 产品质量不随模型抖动；
2. **确定性/可回放**：双跑同 hash、lockstep 就绪——这是"LLM 写自由代码"路线永远给不了的；
3. **可审计/可 diff/可回滚**：数据变更能 review，代码生成不能；
4. **token 经济性**：填表比写代码+调试便宜一个量级——这一条随 agent 化大规模生成反而越来越重要。

建议对外叙事从"弱 LLM 也行"重述为"**任何 LLM 产出都可验证、可复现**"（`weak-llm-thesis-redteam.md` 已有同方向自审）。

**风险二：表达力天花板。** 好消息是本次体检证明缺口是**收敛的而非无底洞**——三个游戏的规则层缺口高度重合（修正聚合、回合相位、牌库经济、对掷判定、演出时序、utility AI），可枚举成 5-6 个 capability。坏消息是按现在"每游戏自炉灶"的惯性，缺口不会自动收敛，只会继续复制第 4 套、第 5 套。

**潜力评级：值得继续压注。** 前提是把下面的债还掉——否则它会长成"一个带着漂亮 manifest 管线的传统手写游戏合集"。

## 六、owner 定调后的重排（2026-07-02 追加）

> owner 拍板：**game-d + game-g 是仅有的两个出口游戏，其余全是 sample**。据此把 §五 的优先级按两条线重排。

### 6.1 产品线（出口质量，直接影响能不能发）

**game-g（底子最好，出货风险集中在一处）：**
- **P0 · 虚胖数据清算**：18/36 天罡零战斗效果、141/156 地煞纯文案——这不是架构债，是**玩家可直接感知的产品 bug**（买到/抽到不生效的卡）。要么实装、要么砍出卡池、要么明确标注未解锁。出货前必须清。
- **P1 · 战斗屏收口**：混血 UI + 6 处 innerHTML 浮层 + coin-flip 死代码。掌机弱 GPU 上每处手写 CSS/DOM 都是黑屏类事故温床（transform:scale 黑屏有前科）。
- 810 行自炉灶战斗核**不阻塞出货**（能跑、种子化、28 个测试文件）——下沉与否归引擎线，降级。

**game-d（两个出口里风险更大的那个，且有窗口期）：**
- **P0 · 地基置换，趁现在**：内容才 1,084 行是唯一的好消息。裸 `Math.random` → 种子 PRNG（双人同步/回放的根，现在不换以后翻倍还账）、手写牌型判定 → 复用 `poker-hand`、combat 纯函数补单测 + 断言平衡 sim 与 combat.ts 一致（消除静默漂移）。内容膨胀前是最后的廉价窗口。
- **P0.5 · 双人技术验证提前**：双人是核心卖点但目前是假按钮，依赖 net/lockstep 基建（主程域）——这是 D 排期的最大未知数，应尽早做 spike 验证而不是留到 M4。
- gdd 自证理论上限 70-85% 纯数据：地基置换时顺势把战斗规则/房间表/流程摆成数据，一次施工两个目的。

### 6.2 引擎线（LLM 命题，受益者恰好就是两个出口游戏）

- **修正聚合下沉（P0 不变，理由更硬）**：不再是"防第 4 个游戏重写"，而是 game-g 已有两套、game-d 的 buff 系统（ALLY_BUFFS）就是第三个直接需求方——下沉一次，两个出口游戏都吃到。
- **对掷判定+平局阶梯下沉（P0 不变）**：game-g 已验证、game-d 骰途是天然消费方。
- **bench 覆盖改为 D+G 优先**（原建议"全部在营游戏"收窄：出口的两个先进 bench + 数据占比/可执行率度量）。

### 6.3 sample 线（降级，但有一条新义务）

- game-e 的双份流程真相、手写 React **不再按产品债催修**。
- **但 sample = LLM 的教材**：game-e 的计分核是全仓最好的正面教材，它的 1,163 行 React 就是最毒的反面教材——LLM 照 sample 学，坏样例会被批量复制。义务二选一：修掉，或明确隔离标注「此文件非范式，勿模仿」。CLAUDE.md 里 game-e"本就走引擎渲染器"的失实豁免必须改掉（否则规则文档自己在撒谎）。
- game-f/h/i/x 维持冻结/sample 现状，不投入。
