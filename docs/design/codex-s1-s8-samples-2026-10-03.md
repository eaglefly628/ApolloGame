## 三、抽样暴露的流程缺陷

### P0 · 门的真实性不足

1. **人门可被文字冒名。** `game-pipeline.mjs signoff` 只查 note 非空，`--by` 任意字符串；Game 112 的 S2/S3/S4/S5/S7/S8 已出现 `Lead-Codex` 签核。`review --by` 和 S7 `scorecard --by` 也只查非空。应把真人签核从 agent 可调用的自由文本写入口移出，绑定经认证的操作身份与任务 ID；独立复查需绑定施工任务 ID、复跑结果和证据。仓库已有 `REQ-PIPELINE-GUARDS`，应优先实施并把验收扩大到“改 JSON/换名字不能造绿”。
2. **可驱动率 0% 仍过 S4。** Game 112 旧 S4 证据明写 `0%`，但门的 `interpretUiWalkthrough` 把它作为警告。对有 UI 入口的游戏，应先执行剧本 `uiEntry` 到达可玩状态；关键剧本动作可驱动率低于门槛则红。Game 112 另有自编 59/59 浏览器走查，说明这是探针接线问题，不等于游戏无法点击。
3. **S8 可先签后验。** Game 112 `pipeline.json` 有 S8 review/signoff，却没有 `evidence.S8`。签核命令应要求本关机器证据与复查均为当下有效；旧 S8 的“共享基线红项不相关”也必须有独立裁决和范围化豁免记录，不能靠 note 自判。

### P1 · 阶段和作品形态对不上

4. **全游戏统一指纹导致无关关卡连锁过期。** Game 112 后续猫资产/动作修改让 S2、S3、S4、S5、S7 的旧复查和证据一起过期。旧结果确需重看影响面，但能力计划无需因每张猫图重新完整审一次。应给阶段定义输入依赖：规则/能力变更影响 S2–S4，画面/资产影响 S5–S7，所有交付变更影响 S8；规格变更始终触发对应下游重验。看板展示“哪些文件使哪项证据失效”。
5. **Game 113 的获准原型无流程位置。** owner 授权非游戏 Web/App 页面用独立 React/CSS，且先做原型、暂缓游戏 S2；当前看板只显示 S1 绿、S2–S8 未开始，无法记录原型截图/响应式/交互验收。`game-skill-audit game113` 当前确实报 React 屏 7、手写 DOM 1、同形手写 2，退出 1。应为一个项目建 `app-prototype` 与 `gameplay` 两类**受范围约束的工作包**：原型包准许该 UI 技术栈并用浏览器/可访问性/视觉门；游戏玩法包仍守 LayoutNode、Tier 与 S2 能力计划。例外只能覆盖非游戏页面路径，不能让游戏玩法逃审。
6. **S5 缺真实视觉目标门。** Game 112 自检文档和截图齐，但 S5 gate 只跑 `game-skill-audit`，有 blessed 标准照才做像素比对；无基准提示后放行。Game 113 有九张预审图，却没有状态/视口配对和评分记录。两例共同证明“有 Gallery 规则、有截图”与“向目标图迭代达标”之间缺一条机器可核的桥。

### P2 · 设计输入与证据管理

7. **Gallery 使用无法审计。** Game 112 采用 LayoutNode/house theme，结构能过审；但没有逐需求的 Gallery section 选择与采用理由。Game 113 非游戏页面不必受 LayoutNode 闭集限制，仍可复用 Gallery 的布局与交互范例；也需要记录哪些适用、哪些不适用。新增 `gallery-map` 作为 S4 选型输入，S5 报告核对采用情况。
8. **视觉参考与实现缺版本关系。** Game 112 的 `claude-design-spec.md` 已声明后续改向覆盖旧线框/截图；Game 113 的 v1–v3 文档保留，V4 预审图又未成为浏览器验收基准。设计任务应指向明确的参考版本、适用屏幕/状态与批准状态。变更后只让受影响的截图与评分失效。

## 五、建议的双样本验收

1. **先修 P0 流程门**：用 Game 112 的既有记录构造回归夹具；agent 以 `Lead-Codex` 签人门、S4 可驱动率 0%、无 S8 机器证据签核都必须明确判红。保留历史记录作审计，不自动改写为“真人通过”。
2. **Game 112 跑视觉循环**：选主厅、馆图、一个房间 Drawer；每屏定参考版本、状态和 1280×800 视口，报告当前图/目标图/差异/分项分数；修一轮后重拍评分。S7 重评反映现在的猫图与动作，S2–S5 只复核被这次改动影响的依赖。
3. **Game 113 跑原型轨**：以 V4 首页的桌面与手机两端为样本，先让用户确认预审稿是否为目标；再把“首屏有什么、推荐卡占比、阅读字号/点击区、今日新鲜/同好何时出现”写成可测条款。React 原型按专项政策过浏览器门；三消/细看等游戏模块待 S2 后单独过引擎门。
4. **成功定义**：两样本都能从 Codex 的同一看板看到阶段/工作包、截图、机器检查、视觉分、返工轮次与下一项阻塞；没有人手改台账或口头说“已对齐”就能过门的路径。
