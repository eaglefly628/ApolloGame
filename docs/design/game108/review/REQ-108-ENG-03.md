## 三、三处**我想请你重点看**的判断（最可能出错的地方）

1. **为什么落点在 `matrix-duel-announce`（Commit）而不是结算系统（Update）**
   —— `ResourceModify` **只有加减、没有 `set`**，所以清零只能发「-当前值」，就必须**读 `Resource`**；
   而结算系统**刻意不读 `Resource`**（读了会与「排 `resource-apply` 之前」合围成环，见文件头定序证明）。
   `announce` 在 Commit、排在 `resource-apply` 之后，读到的正是扣血后的真值 → 天然合适。
   **请核**：这个理由成立吗？有没有更该放的位置？
2. **一拍延迟**：Commit 发的 `ResourceModify` 由**下一拍** `resource-apply` 落地，所以测试里都多 `tick` 一次。
   对局是秒级时区，无感知；但**如果将来有人把两回合压到同一拍，这里会咬人**。
   **请核**：要不要在文件头把这条写成显式约束？
3. **`announce` 的职责变宽了**（播报 → 播报 + 结算副作用）。我选择不新开系统，理由是新系统要读 `DuelOutcome`
   而 `announce` 已 `consumes` 它，拆开就得动消费时机 = 碰定序（超出工单边界）。
   **请核**：这个取舍你认不认？若认为该拆，我按你的判词返工。
