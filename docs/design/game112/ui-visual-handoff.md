# Game 112《星尾会客厅》·页面与视觉表现交接稿

> **接收方**：Crow Code / Claude Code / 产品与 UI 设计。
> **目标**：先完成页面信息架构与高保真设计稿，不直接写游戏实现。
> **流程真相**：[`menu-flow.md`](./menu-flow.md)。
> **产品真相**：[`gdd.md`](./gdd.md)。
> **引擎约束**：正式实现全部使用 LayoutNode 闭集；设计稿不得依赖自由 DOM、任意 CSS 或无法数据化的交互。

---

## 1. 设计任务

请设计一个以“猫始终是画面主角”为核心的桌面横屏产品界面。它需要同时容纳：

- 高保真照片转活视频猫；
- 固定镜头场景；
- 轻量卡牌游戏；
- 照片上传和身份确认；
- 回忆影片与相册；
- 玩具、家具和牌具商店；
- 爱诗生成任务、失败回退和隐私管理。

页面不能看起来像 SaaS 控制台、手游活动大厅或传统餐厅经营 HUD。

---

## 2. 设计关键词

### 应该是

- 安静、亲密、有生活痕迹；
- 喵星但不廉价科幻；
- 高保真猫 + 轻绘本空间；
- 柔软、克制、可信；
- 允许歪斜、磨损、不成套与遮挡；
- 让玩家愿意停留而不是不断点击领取。

### 不应该是

- 完美对称的 AI 豪华咖啡厅；
- 粉色霓虹、遍地猫爪图标的萌系模板；
- 每屏都有五种货币、任务和红点；
- 悲伤纪念馆、墓园、天堂阶梯等直接死亡符号；
- 让用户觉得“付钱才能再见它”的商业压迫；
- 把猫做成人类表情包或会说人话的虚拟主播。

## 3. 当前视觉锚

### 3.1 猫与世界质感

以以下图片作为角色与环境的基准：

- [`visual/cat-art-direction-ragdoll-v2-lived-in.png`](./visual/cat-art-direction-ragdoll-v2-lived-in.png)
- [`visual/scene-cat-play-ragdoll-v1.png`](./visual/scene-cat-play-ragdoll-v1.png)

保留：

- 猫的高保真眼睛、毛色与大毛簇；
- 暖实用光与喵星冷光的轻微对比；
- 旧木材、织物、纸张和磨砂晶体；
- 杯印、划痕、卷角牌、歪牌堆等生活痕迹；
- 猫偶尔发呆、半眯、趴歪和动作迟半拍。

需要继续降低：

- 完美轮廓光；
- 每个角落都漂亮的景深；
- 完全对称的猫脸与场景；
- 所有物品来自同一套软装的感觉；
- 过多飞散细毛导致的离线渲染感。

### 3.2 喵星装饰语言

- 猫爪星座：只作为稀疏刻纹或投影，不做满屏图标。
- 月相与星轨：用于牌面、晶球底座和窗外天象。
- 忆光晶球：磨砂、内部有流动微光和照片残影，不是占卜水晶球。
- 家具：像被很多猫使用过，局部磨损、抓痕和陷下去的软垫。
- 空间：不是地球咖啡店搬到太空，而是喵星上的长期共同生活场所。

## 4. 屏幕与响应式基线 🟡

第一轮设计基准：

- 桌面横屏：1440 × 900；
- 最小桌面：1024 × 640；
- 移动端只画上传、通知与相册关键页，不在第一轮强行把牌桌压成手机版；
- 游戏场景保持 16:9 安全区，菜单可以占用左右抽屉或底部托盘；
- 所有主要操作在大字号和 200% UI 缩放下仍可完成。

## 5. 全局视觉系统

### 5.1 色彩

| 角色 | 建议颜色感 | 用途 |
|---|---|---|
| 馆内暖光 | 燕麦、旧木、低饱和琥珀 | 生活与安全感 |
| 喵星冷光 | 灰蓝、雾青、月白 | 晶球、导航与夜空 |
| 心光 | 淡金偏乳白 | 关系与回忆，不使用艳粉心形 |
| 星砂 | 暗金与黄铜 | 普通经济，不做赌场金币 |
| 危险/删除 | 降饱和砖红 | 仅隐私删除和错误确认 |

避免大面积纯黑、纯白、艳紫蓝渐变和高饱和儿童糖果色。

### 5.2 材质

- 面板像半透明磨砂晶片或旧纸卡，而不是玻璃拟态科技窗。
- 边框不必完全闭合，可有轻微磨损或不均匀线宽，但信息布局必须精准。
- 主按钮像触摸后会亮起的晶石或布面标签；按钮文字优先可读性。
- 卡牌为厚的无涂层纸，有卷角和触摸痕迹。

### 5.3 字体

- 正文：清晰、低疲劳的现代中文字体。
- 标题：可有轻微手写或旧书感，但不使用难读花体。
- 数值：不强调竞技仪表感。
- 敏感说明：语气平静，不用过小浅灰字隐藏。

### 5.4 图标

- 图标数量要少；优先使用物件本身作为入口。
- 猫爪只用于“回到猫身边”或明确猫相关动作，不用作万能装饰。
- 生成任务使用缓慢流动的星点/胶片符号，不使用机器人大脑图标。
- 隐私与删除使用标准易懂图标，不做诗意化隐藏。

## 6. 全局框架

### 6.1 主厅默认态

```text
┌──────────────────────────────────────────────────────────────┐
│ 当前猫名字 · 今日情绪                  星砂     生成状态  设置 │
│                                                              │
│                                                              │
│                     [猫与主厅固定镜头]                         │
│                                                              │
│          晶球                 牌桌               玩具篮       │
│                                                              │
│                                                              │
│     猫咪               回到猫身边               回忆   星砂铺 │
└──────────────────────────────────────────────────────────────┘
```

要求：

- UI 默认透明度低、面积小，几秒无操作后进一步淡出。
- 场景入口有自然视觉提示，不悬浮巨大按钮。
- 点击猫时先出现轻交互，不立刻打开资料面板。
- “隐藏 UI”后仍能通过边缘轻触恢复。

### 6.2 一级页面

一级页面采用“场景仍可见 + 一侧内容面板”或“进入真实场景区域”，避免全屏白底列表。

- 晶球厅：进入空间，不只是卡片列表。
- 回忆廊：暗一些但不是悲伤黑幕。
- 商店：物品摆在场景货架中，详情才用面板。
- 设置：允许使用标准全屏面板，强调清晰与安全。

## 7. 必画关键页面

### 7.1 S10 星尾馆主厅

画面重点：猫占据视觉中心；忆光晶球、牌桌、玩具篮形成三个可感知入口。

需要状态：

1. 正常陪伴；
2. 刚回馆，猫留下离线事件；
3. 生成任务完成但未确认；
4. 离线模式；
5. UI 完全隐藏。

### 7.2 S20 晶球厅

不做商城式角色卡墙。推荐：

- 当前猫的晶球较近；
- 其他已相遇猫以不同亮度分布在空间；
- 官方猫和私有上传猫有明确隐私标识，但视觉地位相同；
- 未相遇猫只显示世界观线索，不显示“SSR 稀有度”；
- “接回自己的猫”是一颗空的柔光晶球，不是带加号的上传框。

### 7.3 S30～S38 上传与相认

上传流程是信任核心，优先级高于商店。

页面必须清楚展示：

- 当前第几步；
- 照片会用于什么；
- 可以随时退出且草稿保留；
- 生成可以在后台继续；
- 主人拥有最终确认权。

S36 身份确认建议布局：

```text
┌──────────────────────────────────────────────────────────────┐
│  身份确认  3/4                                  保存草稿并退出 │
├─────────────────────────────┬────────────────────────────────┤
│                             │  原始照片 1  2  3              │
│   生成的标准头像/侧面/全身   │                                │
│                             │  眼睛  蓝灰 ✓                  │
│        可切换对照视图        │  花纹  左脸重点色 ?            │
│                             │  毛长  中长 ✓                  │
│                             │  独特特征  + 添加              │
├─────────────────────────────┴────────────────────────────────┤
│  [这不像它]                                      [这就是它]  │
└──────────────────────────────────────────────────────────────┘
```

“这不像它”必须和主按钮一样容易找到，不放成灰色文字链接。

### 7.4 S40～S43 星牌桌

构图：略高于桌面的玩家视角，猫在桌子对面，脸与前爪必须持续可见。

层级：

1. 猫的行为；
2. 中央三个星盘；
3. 玩家手牌；
4. 双方星光与当前回合；
5. 暂停和规则帮助。

避免：

- 用大头像框替代真实猫；
- 牌面覆盖猫爪；
- 过度竞技化红蓝阵营；
- 猫输赢后出现人类表情或夸张字幕。

### 7.5 S50～S54 逗猫角

以 [`visual/scene-cat-play-ragdoll-v1.png`](./visual/scene-cat-play-ragdoll-v1.png) 为构图起点。

- 镜头低，玩具从画面下缘进入。
- 中央留出连续拖动路径。
- 猫可以被纸袋、椅脚和沙发边部分遮挡。
- 除玩具切换、暂停和收起外，不显示 HUD。
- 玩累时不弹结算评分，猫自然趴下后出现两个柔和选择：“陪它坐坐”“收起玩具”。

### 7.6 S60 回忆廊

- 每只猫有一条不完全规则的光带，而不是章节进度条。
- 已确认回忆清晰发光；未解锁只有旧物轮廓和一句线索。
- 上传猫的私有内容有明确锁标，但不使用警告红色。
- “最后一天”“离别”等敏感主题不得成为默认推荐卡。

### 7.7 S62 回忆播放

- 视频本身占主导，控件数最少。
- 支持暂停、静音、字幕、退出和“今天不看这段”。
- 播放完成后先停留，不立刻弹奖励。
- 共同纪念物在返回场景后自然出现，而不是用宝箱动画发放。

### 7.8 S70 星砂杂货铺

- 展示物品会怎样改变互动，例如纸袋提供伏击点，而不只展示属性。
- 清楚区分“装饰”“新互动”“牌具外观”。
- 不设置限时倒计时、折扣红角和连续弹窗。
- 购买后主按钮为“放到馆里看看”。

### 7.9 S90～S95 设置与隐私

这组页面可以更标准化、更少装饰，重点是可信：

- 原始照片是否保留；
- 哪些媒体已上传给生成服务；
- 视频缓存占用；
- 删除照片、删除视频、删除整只数字猫的范围差异；
- 导出后文件包含什么；
- 生成暂停不影响基础陪伴。

删除确认不出现“它会永远消失，你确定吗？”等情绪勒索。

## 8. 状态设计

### 8.1 生成中

- 猫已经可用：显示猫在主厅，后台星光缓慢聚集。
- 猫尚不可用：使用主人确认过的头像和局部微动，不显示通用替代猫。
- 文案：“它的更多动作还在准备，你可以先陪它坐坐。”

### 8.2 失败回退

- 不把错误浮在猫脸前。
- 默认继续使用上一版已确认内容。
- 任务托盘中显示“这一段没有生成好”，提供重试/跳过。
- 不使用“生成失败，猫咪创建失败”这种把技术失败等同于猫失败的文案。

### 8.3 离线

- 主厅仍然完整；只在生成入口和云端相册处显示离线标识。
- 玩家仍可陪伴、使用缓存玩具、打牌和看已下载回忆。

### 8.4 减少动态

- 视频可替换成静态关键帧 + 淡入淡出；
- 晶球粒子停止漂移；
- 镜头不推近、不震动；
- 所有信息和操作保持等价。

## 9. 猫的视频层与 UI 关系

设计稿需要把画面分成可实现的层：

```text
前景遮挡：桌沿 / 椅脚 / 纸袋 / 窗帘
实时交互：玩具 / 卡牌 / 点击反馈 / 字幕
猫视频层：身份稳定的分支短视频
空间轻动态：灯光 / 尘埃 / 晶球微光
静态背景：可布置的星尾馆
```

不要设计必须把按钮插进视频像素内部的效果。UI、玩具与卡牌都应有独立安全区域。

## 10. 文案语气

### 推荐

- “它正在准备更多动作，你可以先陪它坐坐。”
- “这张照片有些模糊，眼睛颜色可能不够准确。”
- “这就是它。” / “这不像它。”
- “今天先不看这段。”
- “它趁你不在，把三张牌藏进了纸袋。”

### 禁止

- “复活你的爱宠。”
- “AI 已还原它的灵魂。”
- “连续三天没有来看它，它很伤心。”
- “付费即可解锁它对你的全部记忆。”
- “删除后它将再次永远离开你。”
- “生成失败，请重新创建猫咪。”

## 12. 审稿问题

设计评审必须逐条回答：

1. 关闭所有 UI 后，玩家是否仍愿意看着猫待一会儿？
2. 主厅是否像一个共同生活空间，而不是功能入口大厅？
3. 第一次上传照片的人是否清楚素材用途和删除权？
4. “这不像它”是否足够容易操作？
5. 生成失败后，玩家是否仍能陪伴与打牌？
6. 牌局中猫的脸和爪是否始终可见？
7. 逗猫棒是否能无延迟移动，视频层不会抢走控制权？
8. 回忆页面是否允许今天不面对悲伤内容？
9. 商店是否把奖励送回共同空间，而不是只增加库存数字？
10. 是否出现任何利用失去猫的情绪促付费或促登录的设计？
11. 是否避免了“过度完美、完全对称、统一软装”的 AI 感？
12. 页面结构能否用现有 LayoutNode 控件闭集表达？表达不了的点必须列缺口，不能自行手写逃生。
