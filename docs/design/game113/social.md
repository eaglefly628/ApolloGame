## 1. 一句话

> 老登的乐趣一半在「玩」，一半在「显摆和请教」。这里让他把自己的真东西晒出来，让懂行的老伙计给掌掌眼，逛别人的仓库，再把自己知道的偏门爱好讲给大家听。

## 3. 核心机制：掌眼（众人估品）

这是把「数据结构」和「社交」接在一起的地方，**完全复用每门爱好已有的品相分级维度**，不需要新设计：

```
 老王上传一对核桃（真藏）
        │  选爱好：文玩核桃
        ▼
 系统按该爱好的分级维度生成一张「估品单」
   配对：不配对 / 基本配对 / 天生配对
   皮质：松 / 一般 / 密实
   边：窄薄 / 中等 / 宽厚
   瑕疵：明显 / 轻微 / 无
   包浆：生核 / 初上色 / 红润 / 包浆厚
        │  推给该爱好学识达到「懂行」以上的同好
        ▼
 同好各自勾选（每人一票，可附一句评语）
        │  每个维度取多数票
        ▼
 得出品级（入门 / 普品 / 精品 / 珍品）→ 按该爱好的档位折成雅钱
        │
        ▼
 老王的真藏有了「品级 + 雅钱」，计入他的仓库身价
 掌眼的人：和多数一致 → 「眼力」+1，学识 +1
```

- **参与门槛**：学识达到「懂行」才能掌眼，保证有一点专业度；新人可以围观、点赞。
- **眼力**：掌眼结果和多数一致的比例，是本作最核心的**声望指标**。老登要的「圈内地位」来自眼力，不来自有钱。
- **不是鉴定**：界面明确写「同好估品，仅供参考，不是鉴定意见」。真伪、价格一概不表态。

## 4. 身份与声望

| 指标 | 怎么来 | 展示在哪 |
|---|---|---|
| 玩过几门 | 入坑的爱好数 | 名片（老顽童的荣誉是「杂」） |
| 各门学识与称号 | 找门道、读知识卡、答小考 | 名片、同好圈发言旁 |
| **眼力** | 掌眼与多数一致的比例 | 名片、掌眼列表（排序依据） |
| 仓库身价 | 全部藏品雅钱之和 | 仓库顶部、串门时的名片 |

**不做全服财富榜**（避免攀比和炫富对立）。可以做「本圈眼力榜」「本月掌眼最多」这类比见识的榜。

## 5. 雅钱在社交里的角色

雅钱是游戏内唯一的计价单位（藏品按品级折算，不显示真实价格，见 `collectible-spec.md` §1.5）：

- **首发只做估值和身价**：藏品有雅钱，仓库有总身价，串门时看得到。
- **不能买、不能卖、不能充值、不能提现、不能转账**。这条是防诈骗和合规的底线：可以流动的虚拟货币会引来「代充」「回收」等骗局，也会碰到网络游戏虚拟货币的监管要求。
- **后续以物易物**：交换的是游戏内的藏品（不是实物），雅钱只作为「这两件大致对等吗」的参考。

## 6. 老年人安全红线（必须做）

中老年用户是网络诈骗的重点对象，社区功能必须内置这些防线：

| 红线 | 做法 |
|---|---|
| 不留联系方式 | 自动识别并拦截手机号、微信号、二维码、收款码、外部链接（文字和图片都查） |
| 不撮合真实交易 | 不提供私下买卖、担保、估价收购；「想卖」「回收」「高价收」等词拦截 |
| 私信受限 | 只有互相关注的老伙计之间能私信，私信同样拦截联系方式；陌生人只能在公开评论区说话 |
| 防荐股、保健品、理财 | 知识卡已禁止健康功效与投资承诺；社区发言同样过滤并可举报 |
| 一键举报与拉黑 | 每条内容和每个人都有；被多人举报自动隐藏待审 |
| 实名与内容审核 | 国内上线有 UGC 社区需实名；图片、文字接入云厂商的内容安全审核 |

## 7. 社交后端：A 和 B 是什么意思（给 owner 的白话说明）

**问题**：社交功能要把每个人的数据放在一台大家共用的服务器上。老王上传的核桃、老李的评论、谁关注了谁、掌眼的投票，都得存在「云端」，别人的手机才看得到。

**我们现在的引擎做不了这件事**：它擅长的是在一台手机里把游戏规则算准（收藏、找门道、学识这些），但**完全没有服务器和数据库的部分**。所以社交的部分必须另外找东西来做。有两条路：

| | A：引擎做游戏 + 租一个现成的云后端（🟡 我推荐） | B：整个做成普通手机 App |
|---|---|---|
| 比喻 | 自己装修房子（游戏部分），水电燃气接市政管网（社交部分用租来的现成服务） | 不用我们的装修队，整栋房子交给另一个施工队从头盖 |
| 怎么做 | 收藏、细看、学识、数据校验继续用我们的引擎；账号、同好圈、上传、掌眼投票用现成云服务（如 Supabase、Firebase，或国内的腾讯云开发 / 阿里云）；两者之间做一个**通用接口**连起来 | 用 Flutter、原生安卓 / iOS 之类的普通 App 技术，从头做全部功能 |
| 好处 | 已经做好的数据规范、校验器、AI 量产流程全部能用；这个通用接口以后别的游戏也能复用 | 社区类功能（信息流、私信、推送）有大量现成组件，做得最快 |
| 代价 | 要开发那个接口；云服务要付月费、要有人维护和审核 | 收藏这套数据驱动的做法要重写；不能再复用我们引擎的内容管线 |
| 适合 | 收藏玩法是核心、社交很重但不是纯社区 | 产品本质是一个社区 App，游戏只是点缀 |

**我推荐 A**，理由：我们已经把收藏玩法做成纯数据（加一门爱好不写代码），这是本作最大的资产，走 B 等于放弃它。社交再重，也是围绕「藏品」展开的（晒的是藏品、掌眼的是藏品、串门看的是藏品）。

**owner 只需要回答一句：A 还是 B。** 选 A 之后，下一步由我们评估具体用哪家云服务（国内上线的话优先国内厂商，备案、实名、审核都更顺）。
