## 判断先行：owner 说「像一张图，不像软件工作流」是对的，且有精确机制

不是观感问题，是三条硬约束叠出来的：

| 约束 | 位置 | 后果 |
|---|---|---|
| 批处理**严格串行** | `art-replace.mjs:598` `for (const row…) await genRowAsset(…)` | N 张 = N × 延迟 |
| 服务层**阻塞调用**，子进程 **300s 超时** | `library.py:35` `subprocess.run(…, timeout=300)` | 超过 5 分钟直接被杀 |
| 台账**只在全部跑完后写一次** | `art-replace.mjs:843` `if (res.ok) writeJson(…)` | 被杀 = 元数据全丢 |

而 `art-replace.mjs:537` 的注释白纸黑字写着「**并发留给 zerocraft 层**」——**那个接缝从建起来就一直空着**。
所以不是"没设计"，是设计了没接。

## P0 · 一键全量在真游戏上必然超时，且超时会批量制造「黑户」

**机制**：图片**逐行落盘**（`:659` `writeFileSync(outAbs, …)`），台账**最后一次性写**（`:843`）。
串行 + 300s 上限 ⇒ 真 key 下跑到一半被 SIGKILL ⇒ **图片已在磁盘、台账一个字没写** ⇒ 这批图全成黑户。

**规模**：game-g 110 行 · game-i 103 行 · game101 69 行。按业界文生图 10~30s/张，
110 张 = **18~55 分钟**，远超 300s。**即「⚡ 一键全量」对现有大游戏根本跑不完。**

**复现**：`grep -n 'timeout=300' main_entry/library.py` + `sed -n '598p;843p' scripts/art-replace.mjs`；
或配真 key 对 game-g 点一次一键全量。

**这条同时解释了「黑户」的第二个来源**——与 vendored 资产那批（见 `REQ-ARTGUARD`）机制不同、后果相同。

## P1 · 在 UI 里改提示词，**被完全忽略**

**机制**：`dialectPrompt` 主体优先级是 `row.prompt` > `query+desc`（`:357`），
而 `resetRow` 改的是 `row.query`、**不动 `row.prompt`**（`:688`）；
面板又把输入框预填成 `r.prompt || r.query`（`ArtLedgerPanel.tsx` 卡片 onClick）。
⇒ 人改了框里的字 → 存进 `query` → 生成仍旧用 `row.prompt` → **看起来"改了没反应"**。

**复现**（已跑）：构造 `{query:'旧', prompt:'早先回填的完整提示词'}`，改 `query` 后
`dialectPrompt` 输出主体**一字未变**；删掉 `prompt` 字段后 `query` 才生效。

**注**：这与 owner 早先提的「提示词精简（subject 从 `query+desc` 收敛成 `query`）」是同一处代码，
建议合并处理——**修的时候顺手把优先级语义写死进注释**，否则还会再犯。

## P2 · 无并发保护：两个批处理会互相整份覆盖

台账全程**无锁**（grep `lock` 在三个美术模块里零命中）。`batchGenerate` 的形态是
「读整份 ledger → 内存改 → 最后整份写回」。⇒ 批处理 A 与 批处理 B（或 A 与单槽重生成）并行时，
**后写的整份盖掉先写的，先者全部结果静默丢失**。

**这条是「想并行铺开」时第一个会踩的坑**——在做并发之前必须先解决，否则并发=数据丢失放大器。

## P3 · 台账写盘非原子

`paths.py:124 _write_json` 与 `art-replace.mjs:43 writeJson` 都是直接 `write_text` / `writeFileSync`，
**没有 tmp + rename**。进程在写台账的瞬间被杀 ⇒ 文件截断 ⇒ JSON 解析失败 ⇒ **整个游戏的台账丢失**。
与 P0 叠加尤其危险：300s 超时的杀进程窗口，正好可能落在写盘那一刻。

## P4 · CLI 回执只认 stdout 最后一行

`library.py:38` `line = out.splitlines()[-1]`。任何适配器/后处理在 JSON 之后多打一行
（警告、进度、第三方库噪声）⇒ 解析失败 ⇒ 端点报「解析失败」，**而实际工作已经做完了**。
表现为"报错了但其实成功了"，属最难查的一类。

## 建议：并行化 = **重组既有能力**，不是造新东西

三步，按「便宜→贵」排，**每步单独可交付**：

### 第一步：接已有的 job 基座（✅ PST 域·解决阻塞+无进度+超时）
`jobs.py` 已有完整的线程 job 基座（`_GEN_JOBS` + 锁 + `handle_generate_job_start` +
`/api/generate/job` 轮询），**LLM 生成线在用、美术线没接**。把 `/api/art/batch` 改成
「起 job → 返回 jobId → 前端轮询进度」即可：阻塞没了、进度有了、300s 上限也随之消失
（job 在后台线程里，不受 HTTP 请求生命周期约束）。**零新造，纯接线。**

### 第二步：逐行落账（🔒 Lead 域·小改·**必须先于第三步**）
`batchGenerate` 每行跑完即写台账，而不是攒到最后。这样任何中断都只丢当前这一行，
且**不再产生黑户**（图片与台账同步推进）。P0 的杀伤力主要来自这里。

### 第三步：有限并发 + 单游戏写锁（🔒 Lead 域）
`for await` 换成 N 路并发池（建议 4~6，受供应商限流约束），**配合单游戏写锁**解决 P2。
注意顺序：**没有第二步的逐行落账、没有写锁，直接上并发 = 数据丢失放大器**。

### 配套
- P3 原子写（tmp + rename）——两边各一行，属基础卫生。
- P4 回执改成「扫最后一个可解析 JSON 行」而非死认最后一行。
