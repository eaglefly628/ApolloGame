# 雀宴 game-b · 数据驱动 / 积木库消费 review

> owner 2026-07-21 提问：「这个麻将游戏的数据驱动成分在哪里？多少用积木库、多少自己写？希望大多数来自积木库。」
> 本 review = PE-B 据真实代码（`src/games/game-b`·3617 行非测试）+ `game-skill-audit` + 红线 grep 的证据化回答。数字口径以 git 现状为准。

## 0. 一句话结论

**表现层（UI/渲染/缩放/随机）= 100% 积木库，零手写逃生**；**规则核（麻将番符/状态机）= 自写 TS 解释器**，只借引擎 PRNG。
「大多数来自积木库」对**表现**成立、对**规则**不成立——**而规则本就该是代码**（owner 2026-07-11「复杂优先」+ TS 卡带例外已背书复杂游戏写游戏层 TS）。这不是欠账，是对的架构。

## 1. 从积木库拿了什么（消费·非自写）

## 3. 为什么规则核该自写（不是宪法违背）

- **宪法尺子**「最弱 LLM 能否产出同样**数据**？」——针对**内容**（关卡/UI/数值），不针对**规则解释器**。宪法明言"代码只属于确定性解释器"；game-b 规则核**正是**这样一台解释器（纯函数·可审计·可复现·12 测文件钉口径）。
- **owner 2026-07-11 拍板**：价值排序「能出复杂的东西=第一要素·最弱 LLM 尺子降级」+ TS 卡带例外背书复杂游戏写 `logic.ts`。**日麻番符=典型"复杂的东西"**——役种识别/和了形分解/符算/役满累计是真规则逻辑，不是能抄的表。
- **强行数据化 = 过度设计**：把 yaku 做成「数据表 + 游戏层自写解释器」正是宪法点名禁的**虚胖数据**；沉成引擎「麻将能力」又是**无脑加宽引擎**（麻将专用·别的游戏不复用）。两条都被宪法反对。

## 4. 能再往积木库推的（可选·owner 定夺·非必须）

1. **yaku 定义半数据化**：把役种做成 `{name, han, predicateKey}` 表 + 小解释器——收敛"魔法常量"面，但谓词仍是代码，边际收益小、且有滑向虚胖数据的风险。**建议不做**（除非 owner 要）。
2. **UI 投影更多走 bind**：牌桌太动态，投影代码合适；不建议硬改。

## 5. 与「美术替换」的关系（owner 下一步）

美术已是数据：牌面/立绘 = PNG 资产（`faceUrl`/`OPP_TACHIE` 引路径）、皮 = 主题令牌。**换美术 = 换资产文件/asset-index 条目，零改代码**。
**唯一缺口（audit 🟡）**：game-b 资产**未登记美术台账/asset-index**（现为本地 vendor 占位）。要让"美术替换"走统一资产管线（provenance/授权/去背/风格包），需补 game-b 美术台账（走 PA/asset-manager）。这是下一步 art-replace 的前置。

## 6. 结论

- 表现/随机/缩放 = **满分积木库**，是宪法理想态，保持。
- 规则核 = 自写确定性解释器，**符合 owner 复杂优先口径**，正确。
- 下一步「美术替换」的真前置 = **补美术台账接资产管线**（不是改代码架构）。
