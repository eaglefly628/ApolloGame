# 条款追踪 · 策划细则→机器验收（REQ-SPECTRACE · Lead 2026-08-04 · owner 令）

> owner 原话意图：复查不靠人看——对齐策划文档后，**按文档细则/每条需求的细则收工**；要一个持续（无限）
> 更新的验收循环。判词：现有验收剧本 conformance 已是「细则→机器证」的单点形态，缺的是**全覆盖追踪**
> （没有机制保证每条细则都有检查）与**活文档同步**（文档改了，旧检查不会自动失效）。本案补这两块。

## 一、三件套

1. **细则编号（策划文档侧·GD 写）**：GDD/需求文档里每条可验收细则挂稳定编号标记，行内格式
   `【R-<游戏>-<序号>】`（如 `【R-A-013】一四进贡：…`）。编号一经使用不复用；细则废除=编号标 `[废]` 留痕。
   最弱 LLM 尺子：GD 写文档时顺手编号，零新工具。
2. **追踪矩阵（数据·`docs/design/<game>/spec-trace.json`）**：每条编号 → 它的验收物清单：
   `{"clause":"R-A-013","checks":[{"type":"scenario","id":"..."}|{"type":"test","name":"..."}|{"type":"audit","rule":"..."}|{"type":"probe","id":"..."}|{"type":"human","note":"..."}],"blessedHash":"<细则文本哈希>"}`。
   `human` 型合法但**单独统计占比**（品味类细则可人判，但人判比例上报表——防「全推给人判」逃逸）。
3. **守卫（`scripts/spec-trace-guard.mjs`·退出码）**：每跑一次判四类：
   - **未覆盖**：文档有编号、矩阵无条目 → 红（逐条点名）；
   - **死引用**：矩阵指向不存在的剧本/测试/规则 → 红；
   - **过期**：细则文本哈希 ≠ blessedHash（**文档改了**）→ 该条全部验收物标 ⚠stale，红——这就是
     「无限更新」的发动机：策划一改细则，受影响检查自动失效，逼着循环重新对齐，绿不了不许收工；
   - **孤儿**：矩阵条目指向文档里已不存在的编号 → 红。
   重新对齐 = 验收物改好真跑绿后，`--bless <clause>` 更新哈希（bless 动作留 git 痕）。

## 二、闭环（谁动谁）

策划改细则 → 守卫标 stale → GD 补/改验收剧本（剧本作者=GD 铁律不变）→ PE 改实现跑绿 → bless →
守卫绿。**复查门升级**：复查 session 的清单第一项从「自由核证」变「跑 spec-trace-guard + 抽查矩阵映射
是否名实相符」（防「编号挂了个不相干的检查」——映射质量抽查仍需复查智能，但覆盖率与新鲜度全机器化）。

## 三、落地节奏

- **V1（本单）**：守卫三件套 + 试点接入**一个游戏**（game-c：GDD 全、剧本 9 条、活跃）——GD 侧把
  game-c GDD 核心细则编号化（首批 ≥15 条）、矩阵首版、守卫真跑红→绿全过程走一遍。守卫先独立跑，
  **不接门禁**（试点期）。
- **V2（试点后）**：接 S4/S5 机器门 + 复查门清单改写 + 其余游戏滚动接入 + stale 自动开工单（与管线
  软件编排器对接：stale 条款→自动生成阶段会话工单）。
- 验收物类型 `probe` 预留给渲染探针（REQ-RENDERCHECK R1/R2/R3）——两案汇流处。

## 四、红线

编号不复用；bless 必须附真跑绿证据（守卫拒绝对红检查 bless）；human 型占比进守卫报表；
矩阵是数据不是代码（守卫是通用解释器——数据驱动宪法同款结构）。
