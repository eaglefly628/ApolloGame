Problem

传统游戏开发对 AI 是黑箱

🚨

紧耦合

传统引擎的游戏逻辑深度耦合。加一个"中毒"效果，可能需要改战斗系统、UI 系统、存档系统三处代码。

🧠

无语义

代码是给人读的，不是给 AI 读的。变量名、函数签名没有标准化语义，AI 无法理解"这个函数是做伤害计算的"。

🔒

不可组合

游戏机制不能像乐高一样拼装。想让 AI 自动设计关卡？它需要先理解整个代码库——这不现实。

核心矛盾：AI 需要结构化、语义化、可组合的接口，而传统引擎提供的是非结构化、隐式、紧耦合的代码。

Solution

Apollo 把游戏拆成可组合的能力单元，
用语义化协议让它们自动协作

Semantic Protocol

Component 语义词汇表

每个 Component 有语义分类。AI 看到分类就知道如何使用 — 资源绑进度条、事件触发一次后消失、意图来自外部输入。

语义分类 Component TypeScript 签名 AI 理解
Resource Health { current: number, max: number } 有上限的数值 → 绑定进度条 → 可被增减
Resource Mana { current, max, regenRate } 同上，可自动回复
Event DamageEvent { amount, damageType } 一次性触发 → 被 consume 后消失
Event HealEvent { amount } 一次性触发 → 正向资源变化
Intent AttackIntent { target: EntityId } 来自外部输入 → 被 System 转化为 Event
Marker Dead { } 存在即有意义 → 触发死亡逻辑/UI
Config Attacker { baseDamage, target } 长期存在 → 描述实体属性

AI-Native

AI 如何使用 Apollo

AI 不需要理解整个代码库。它只读 Manifest（能力声明），然后生成 Assembly（装配蓝图）。

1

📖 AI 读取已有 Capability 清单

"有 health（资源类，current/max）、damage（事件类，读 AttackIntent 写 DamageEvent）、shield（资源类，可吸收伤害）..."

2

🧠 AI 理解语义关系

"DamageEvent 会被 HealthSystem 消费。如果我要加一个护盾，只需在 DamageEvent 到达 HealthSystem 之前拦截它，修改 amount。"

3

📝 AI 生成新 Capability

输出一个 ShieldCapability：声明 reads: [DamageEvent, Shield], writes: [DamageEvent, Shield]。引擎自动把它插到正确的位置。

4

🎮 AI 生成 Assembly 蓝图

JSON 描述：哪些 Capability 组合、创建哪些 Entity、初始 Component 值。一键实例化一个完整游戏。

关键洞察：AI 操作的粒度是 Capability 和 Assembly，不是源代码。
这把 AI 游戏开发从"写代码"提升到"设计游戏"。

Manifest Spec

Capability Manifest — AI 的接口文档

// health.capability.ts — 完整 Manifest 示例 export const healthCapability = { manifest: { id: 'health', name: '生命值系统', version: '1.0.0', // 语义标签 — AI 用这些理解能力的本质 semantic: ['resource', 'health', 'vital'], // 数据合约 — System 间的通信声明 components: { provides: ['Health'], reads: ['DamageEvent', 'HealEvent'], writes: ['Health'], consumes: ['DamageEvent', 'HealEvent'], }, // 可调参数 — AI 可以微调 config: { minHealth: { type: 'number', default: 0 }, deathThreshold: { type: 'number', default: 0 }, }, // 表现层建议 — 告诉 Presenter 怎么展示 ui: { Health: { template: 'Bar', color: '#4CAF50' } } }, systems: [healthSystem], }

📡 provides

我定义了哪些 Component 类型。其他 Capability 可以读写这些类型。

👀 reads

我需要读取哪些 Component。引擎保证这些 Component 的写入者在我之前执行。

✏️ writes

我会修改哪些 Component 的数据。引擎检查写冲突。

💨 consumes

我读完后会删除。这些是"事件"型 Component — 只活一帧。

⚙️ config

可调参数。AI 可以在 Assembly 里覆盖这些值来微调行为。

Assembly

World Assembly — AI 的产出物

这就是 AI 需要生成的东西。一份 JSON/TS 蓝图，描述一个完整的游戏世界。

// demo.world.ts — Assembly 蓝图 // AI 生成这个文件来 "创造一个游戏" export const demoWorld: WorldBlueprint = { // 1. 选择要加载的能力 capabilities: [ 'attack-input', 'damage', 'health', 'heal-input', // ← 加一行就有治疗 ], // 2. 定义实体和初始数据 entities: { player: { Attacker: { baseDamage: 10, target: 'dummy' } }, dummy: { Health: { current: 100, max: 100 } } }, // 3. 覆盖默认配置 config: { 'damage': { baseDamage: 15 }, 'health': { deathThreshold: 0 } } }
🧩

声明式

不写逻辑代码。只声明"我要什么能力、有什么实体、初始数据是什么"。

🤖

AI 友好

结构固定、语义明确。AI 不需要理解代码，只需组合已有 Capability。

🔄

热加载

修改 Assembly → 引擎重新实例化 → 游戏即时变化。设计迭代零等待。

🔍

可验证

引擎检查 Assembly 的合法性：依赖的 Capability 是否存在、Component 类型是否匹配。

Tech Stack

技术选型

💠

Engine Core

  • TypeScript — 类型系统约束 Component Schema
  • 零依赖 — 可在 Node/Browser/微信运行
  • 拓扑排序 — Kahn's algorithm 基于 reads/writes
  • ~500 行核心 — 极简实现，易审计
⚛️

Presenter

  • React 18+ — Concurrent Mode，无撕裂渲染
  • useSyncExternalStore — 安全桥接 Engine 状态
  • Template + Binding — UI 原子与数据映射分离
  • CSS Variables — 主题系统零 JS 开销
🛠️

Tooling

  • Vite — 极速 HMR，TypeScript 原生支持
  • Vitest — Engine 无头测试
  • Storybook — Template 组件可视化开发
  • pnpm workspaces — engine/presenter 包隔离

跨平台策略： Engine 层不变，Presenter 层按平台替换： React DOM → Web |  Canvas 2D → 微信小游戏 |  React Native → App
