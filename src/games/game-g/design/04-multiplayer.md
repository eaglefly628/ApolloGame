# 04 · 多人（outcome-first 让它重新可行）

> 承 `00` 回驳表 R-1。本篇说明为何 outcome-first 把"实时多人"从"被回驳"变成"可行"，以及它的形态。

---

## 一、服务器权威 outcome-first

```
   玩家干预命令(改 favor/重翻/护盾)
        │ 各 client 上报
        ▼
   ┌──────────────── Server(权威) ────────────────┐
   │ 跑确定性 decideFaceUp(favor, seed)            │
   │ 按拍合入干预命令 → 重算确定性整数胜负           │
   └───────────────────┬──────────────────────────┘
                       │ 广播「每牌正/反」整数结果
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
     client A       client B       client C
   各自用 3D 翻牌「演出」同一份整数结果（表现各端略不同也无妨）
```

- **权威状态 = 整数胜负**（规则 + 种子）。server 跑唯一确定性 `decideFaceUp`，client 只负责把结果演成 3D。
- **多人干预**：很多玩家同时"改命"→ server 按拍合入 → 重算 → 广播。命令总线 = `net/services` 基建（infra，非新游戏能力）。

---

## 二、为什么浮点债不再卡 gameplay（R-1 的化解）

- 初版"物理决定胜负"需要**实时跨端物理 lockstep**——这是引擎最硬的跨端浮点骨头（不同架构/JIT 的 1-ULP 差异经积分发散）。**那才是 R-1 被回驳的原因。**
- v2 outcome-first 下：**物理翻牌是 client 表现**，各端粒子/翻滚略不同**不影响整数胜负** → 跨端浮点债被隔离在表现层、**够不到 gameplay**。
- 结论：**outcome-first 直接扫清了实时多人的浮点障碍**，这正是初版回驳的实时多人在 v2 下变可行的根因。

---

## 三、排期与边界

- **多人 = Phase-4**（见 `05` 路线）。MVP 单机优先（同机确定性已扎实），把玩法跑透再上多人。
- **传输层**：真·远程传输（WebSocket/WebRTC 信令 + 帧/命令收发）是仓库既有开放缺口（参考 `requests.md` REQ-018，跨 game 共用）；同机两标签 lockstep 已验。
- **边界**：server 权威 + 命令总线 = `net/services` 基建，不是游戏数据能力；与确定性引擎解耦。
