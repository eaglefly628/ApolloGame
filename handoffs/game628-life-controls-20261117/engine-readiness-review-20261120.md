# Game628 小生活游戏引擎接入评估

评估日期为 2026-11-20。本轮按 owner 最新提出的小生活游戏方向，审查 `game628-life-controls-20261117` 及其 11 月 20 日参考街区更新。该方向尚未形成签署的完整玩法规格，本单用一日生活闭环界定最小验收范围。旧工作树 `docs/design/game628/capability-plan.md` 仍是《最后的火柴》，不能据其阶段状态判断生活游戏完成度。

评审结论为可以用现有引擎开始生活玩法竖切。当前可确认的是行走、换街和美术表现底座，生活规则与持久化接入尚未交付。本单是代码和数据接线评估，未执行这一版本的浏览器视觉验收，也未宣告独立完整 review 门通过。

| 优先级 | 发现与依据 | 对生活游戏的影响 | 处理范围 |
|---|---|---|---|
| P0 | `host.ts:createView` 每次新建 Engine 并加载初始 manifest；`switchScene` 成功后 dispose 旧 View；没有生活状态提取及恢复接线 | 引入余额、居民关系和库存后，跨街返回需要保留它们，不能直接沿用每次初始装载的语义 | 定义一个跨街区的游戏会话状态归属，复用现有存档模块；不要仅把渲染场景快照当完整生活存档 |
| P0 | `streets` 的规则组件只有换街 Flag；`art-street` 和 `reference-walk` 未装 Resource、CraftRecipe、DialogueScript 或生活流程 | 暂无赚钱、购买、消费、居民反馈和下一日的连续玩法 | 先装配一份纯数据闭环，禁止把美术场景通过当玩法通过 |
| P0 | `environment.ts` 接收 performance.now 及手动昼夜选项，修改表现字段；已有用例明确保证不改模拟状态 | 店铺营业、居民作息和按日结算缺少共同的权威游戏时间 | 模拟 tick 驱动日期和时段，存档保存游标；灯光从该时段投影。暂停、对话及换街期间是否推进须写入玩法规则 |
| P1 | `configFor` 对每个访问过的场景使用 assets.load 并缓存配置；host 仅 pagehide 时 assets.clear | 释放旧 renderer 后，资产管理器仍可持有加载结果；街区增加时需要检查内存增长 | 按目标版本核对资源组 preload/release 契约，接引用生命周期，实测多次往返的内存，不根据实体数量推断 GPU 回收 |
| P1 | `Inventory` 已有格位及 invAdd/invRemove/invMove 纯函数；`CraftRecipe` 消费 Resource 并钳制 gains | 不能仅凭两件能力存在，就承诺扣钱和写入有限背包全成功或全失败；满容量时尤其要防扣钱后截断 | 首版固定商品用 Resource 计数并显式检查上限。需要格位、唯一物品或物品属性时另做接缝证明，确认表达缺口后提交 A/B 裁决 |
| P1 | 原型和参考街区仍在 handoffs，当前正式设计入口属于旧题材 | 入口、资产版本、验收报告容易对应到不同产品 | 为生活版本独立记录产品入口、玩法契约和候选资产状态，保留旧童话成果；正式接入时统一构建与存档版本 |

已查 `src/assembly/capability-registry.gen.ts`、`src/assembly/capability-registry.ts`，并对照 events-logic、save-platform 手册及实际实现。下表中的现有能力只表示可重组底件，不表示 Game628 已装配。

| 生活需求 | 可复用底件 | 首版边界与验收 |
|---|---|---|
| 走近店铺、交互与离开 | `t2-zone-occupancy`、`t2-keybind`、`t2-event-when` | 出范围不能购买，UI 和键盘统一走具名输入 |
| 余额、商品数、关系值 | `f1-resource`、Flag/State | 固定整数金额、固定 ID 资源；关系配事件条件与记忆 Flag，明确重复互动的次数限制 |
| 购买、工作报酬、消耗物品 | `t2-craft-recipe` | 所有 costs 可负担才成交；收益容量必须显式约束。余额不足、满容量、重复输入和读档重放另验 |
| 简单对话与居民事件 | `t3-dialogue`、`t3-flow`、`t2-event-when` | 第一位居民可按状态回应、一次性记住交付；多居民通用日程和跨区寻路需另做接线证明 |
| 一日生活与商店营业 | `t3-flow`、`t3-timeline`、`t2-over-time` | 先用离散早/午/晚阶段重组。存档和换街不重置日期或重复结算 |
| 保存与恢复 | `SavePort`、信封/codec/migrations 或 `SaveSystem` | 先确定单一存档契约。保存余额、物品、日期、事件领取和居民记忆，恢复后继续运行验证 |
| 拿取、递交和挥手 | 已有角色播放；复杂交互复用 Attach3D/IK3D 路线 | 事件以模拟结果为准，动画中断不能多发奖励。动作库与当前角色仍需逐项接入 |
| 生活操作面板 | LayoutNode、mountUI、现有 house 主题 | 画面只投影世界，按钮只发信号，购买结果由真实余额和物品状态确认 |

货币沿用讨论中的单一基础游戏币。现金、存款是明确的余额账户，库存和股票持仓各自记录。第一条闭环只需一个钱包和明确价格。双账户转账需验证接收方上限，防止 CraftRecipe 的 gains 钳位吞掉已扣金额。外部行情留作后续独立输入，当前不把每日经营依赖在联网服务上。

本轮建议的实施验收脚本如下。事件文本和价格是待产品设计确认的数据，不构成已签署题材。

1. 玩家进入街区，拥有可见余额，走近店铺收到交互提示。
2. 完成一次简单工作获得报酬，重复触发受到该工作的规则约束。
3. 购买一份固定商品，余额和持有数量在同一次结算中改变。
4. 把商品交给一位居民，物品扣除，居民回应改变并保留事件记忆。
5. 进入下一条街再返回，余额、商品、居民记忆和当前时段保持。
6. 回家结束一天，推进日期，重置明确允许每日重复的工作；一次性事件保持完成。
7. 保存并重新启动，恢复到相同游戏状态。买不起、重复输入、结算边界、坏档及旧档均有明确结果。

执行顺序为会话状态归属及存档契约、纯数据交易和居民事件、一日流程、真实角色交互和最终画面，再扩展商店与街区。前四项共同完成后才能称首个生活玩法竖切通过。当前没有足够证据提出一套全新经济、日程或开放世界引擎的实施申请。
